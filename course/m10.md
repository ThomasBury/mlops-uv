# M10. Predict delivery delays at booking

A parcel operator wants to flag shipments that may miss their promised delivery time as soon as they are booked. Build a probability forecast and give a reviewer enough evidence to tell whether it uses facts the operator could have known at that point. Allow 60 minutes for a first attempt.

## Open the starter

Use Bash and Python 3.12 from the repository root. The exercise uses two synthetic CSVs and the Python standard library. You can start here directly. Keep your edits and reports in a scratch directory.

```bash
m10="$(mktemp -d)"
cp course/m10_starter.py "$m10/attempt.py"
py=(python3.12)
# If you use uv to supply Python, use py=(uv run --no-project --python 3.12 python).
data=course/fixtures/m10
```

### Data dictionary

All timestamps are UTC. Each row of [`bookings.csv`](fixtures/m10/bookings.csv) describes one parcel, and [`status_events.csv`](fixtures/m10/status_events.csv) reports scans from parcels moving through their depots.

| File | Fields | Meaning |
| --- | --- | --- |
| Both | `parcel_id`, `depot` | Stable parcel ID and handling depot. |
| Bookings | `booked_at`, `promised_at` | Time the parcel was booked and delivery deadline supplied at booking. |
| Bookings | `delivered_at`, `outcome_available_at` | Actual delivery and the time its outcome reached the operator. Both are blank if the outcome is unresolved. |
| Status events | `occurred_at`, `available_at` | Time the scan happened and the time its record reached the operator. Availability is at or after occurrence. |
| Status events | `status` | Either `on_track` or `capacity_warning`. Within a depot, the supplied scans have distinct occurrence times. |

## 1. Define what can be scored (10 minutes)

Write a short contract for the reviewer. State what one prediction represents, what counts as late, which timestamp sets the feature cutoff, what is known at booking, and when the label can be used. A delivery exactly at the promise is on time. Use `P01`, `P02`, and `P12` to illustrate your rule. For `P01`, compare one instant just before its outcome becomes available with the instant it arrives.

Implement `label_at` in your copy of the [starter](m10_starter.py). Return `1` for late, `0` for on time, or `None` when the outcome is unavailable at the requested instant.

## 2. Specify the depot feature and baseline (20 minutes)

At each booking, use the most recent scan by occurrence time from another parcel at the same depot, among scans **available at or before booking**. Encode a capacity warning as `1` and use `0` for an on-track scan or empty history. Write down which scan you expect the feature to use for `P08`. Compare the records for `P05` and `P07`.

Read `booking_feature`. The starter contains a timing defect. Keep that version for your first evaluation so you can see what the defect does to the reported comparison. For the baseline, every evaluation parcel receives the same probability, the fraction late among the eligible training parcels.

## 3. Compare on a later period (20 minutes)

Pick a training boundary before looking at losses. Use midnight UTC on January 7, 8, or 9, 2030. January 8 gives the comparison in the worked solution. Score at midnight UTC on January 16. Record both dates and use the same dates for the first run and the repair.

- For training, include parcels booked strictly before the training boundary whose labels were already available by that boundary.
- For evaluation, include parcels booked from the training boundary through the scoring time whose labels are available by the scoring time. Keep a count of bookings whose labels are still missing at scoring time.
- For both periods, calculate the feature at each parcel's own booking cutoff. Fit the candidate on the training parcels. For each feature value, use `(late_count + 1) / (parcel_count + 2)` as the estimated probability. The added counts keep the forecast inside `(0, 1)` even if every parcel in a group has the same outcome.

Implement `evaluate` in your scratch script. Return a dictionary with the following fields. The starter records the declared dates and writes the JSON. `log_loss` scores one probability against one observed outcome using the natural logarithm. Compute both losses on every evaluation parcel before averaging the within-parcel differences.

| Field | Contents |
| --- | --- |
| `training_ids` | IDs of the parcels used to fit both models. |
| `predictions` | One row per eligible evaluation parcel with `parcel_id`, `label`, `baseline_probability`, and `candidate_probability`. The row IDs identify the evaluation membership. |
| `mean_log_loss` | A dictionary with the average `baseline` and `candidate` losses. |
| `mean_paired_difference` | Mean of candidate loss minus baseline loss, paired by parcel. A negative value favors the candidate on this sample. |

```bash
train_date=2030-01-08
score_date=2030-01-16
"${py[@]}" "$m10/attempt.py" "$data" "$train_date" "$score_date" > "$m10/before.json"
```
