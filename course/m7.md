# M7. Automate and audit the forecast

The weekly replay finishes successfully. Its candidate has slightly lower mean log loss than Elo. Should the run approve the candidate? First build the evidence from the pinned archive, then make the decision with the rule you used in [M6](m6.md). Finish by investigating a plausible prediction from a checkout you haven't seen before.

## Rebuild the evidence in a fresh directory

From the repository root, use Bash, uv, Python 3.12 and `just`. The [justfile](../justfile) gives the commands from earlier lessons names you can use locally and in CI. Open it and trace the three calls inside `forecast-candidate`.

| Recipe | What to inspect |
| --- | --- |
| `just forecast-prepare RESULTS` | The pinned CSV becomes canonical Parquet. The preparation report records the source and content digests. |
| `just forecast-train RESULTS BUNDLE` | Temporal selection and the fitted pipeline are saved together with membership, search results and artifact digests. |
| `just forecast-evaluate RESULTS BUNDLE` | The frozen candidate and baselines score the same final fixtures. The output includes the paired comparison and one row per match. |
| `just forecast-test` | The forecast suite exercises the cutoff, training and evaluation, HTTP parity, monitoring and rollback. |
| `just forecast-serve RESULTS BUNDLE PORT` | A local worker loads the specified history and frozen bundle as in [M5](m5.md). |

```bash
m7="$(mktemp -d)"
candidate="$m7/candidate"
(
    set -eu
    just forecast-test
    just forecast-candidate "$candidate"
)
```

`forecast-candidate` creates the run directory, so give each attempt a new path. You can keep a partial run to see which stage failed. Training and evaluation store their MLflow records under the run directory as well.

Read [`review_candidate`](../src/acebet/historical_monitoring.py). The forecaster checks the history digest and the model bytes against the selection record. The review checks that the evaluation identifies that selection and model, then replays F01 and recomputes the Elo gate. This is the report it returns.

```python
return {
    "selection_sha256": selection_hash,
    "evaluation_sha256": sha256_file(evaluation_path),
    "fixture": forecaster.predict(fixture).model_dump(mode="json"),
    "gate": promotion_check(bundle / "final", "logistic_tuned", "elo"),
}
```

Trace an identity through the files. Compare `fixture.model_sha256` in `validation.json` with `model_sha256` in `bundle/final/evaluation.json`. Compare `gate.forecasts_sha256` with `forecasts_sha256` in that same evaluation. The replay should report F01's noon cutoff and a first-player probability near `0.475945`. Model and report digests identify this run's files. Use the numerical tolerances from [M4c](m4c.md) when comparing independently rebuilt forecasts.

## Make approval explicit

Predict the gate result before reading `accepted`. On 369 matches, the mean candidate-minus-Elo log loss is about `+0.00340`. The weekly 95% interval is about `[+0.00019, +0.00547]`. The rule requires the upper endpoint to be below zero, so the archive gives `accepted: false`. The build succeeds because it produced a valid review of the candidate.

```bash
(
    set -eu
    status=0
    just forecast-promote "$candidate" > "$m7/promotion-attempt.json" || status=$?
    test "$status" -eq 1
    cmp "$candidate/validation.json" "$m7/promotion-attempt.json"
    test ! -e "$candidate/bundle/promotion.json"
)
```

`forecast-promote` recomputes the review from the run's inputs. When the gate accepts a candidate, the command writes a dated `bundle/promotion.json`. Activation requires a separate action to start a worker with the selected model and history. To see the approval path with controlled scores, read [`test_candidate_review_and_explicit_promotion`](../tests/test_historical_serving.py), which the forecast suite just ran. Its synthetic scores test whether an approval record is written. The archived comparison still stands.

## Read the same evidence in GitHub Actions

In [`forecast.yaml`](../.github/workflows/forecast.yaml), find the build command and its output path.

```yaml
- name: Build and replay a candidate
  run: just forecast-candidate "$RUNNER_TEMP/forecast"
- name: Verify the checkout stayed unchanged
  run: test -z "$(git status --porcelain)"
```

Pull requests and pushes to `main` build a candidate. The [CI workflow](../.github/workflows/main.yaml) runs the project test suite for those events. The Monday 06:23 UTC schedule and manual dispatch also run `forecast-test` in the forecast job. GitHub runs the schedule from the latest commit on the default branch. The job uses read-only repository permissions and uploads the candidate evidence. [GitHub Actions workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

In **Actions**, open **Historical forecast** and choose a run whose event is `schedule`. If none is available, use a successful push run to practice reading the artifact. With write access and the workflow on the default branch, **Run workflow** lets you rehearse the scheduled steps on demand. Record the event, commit and run URL. On the run summary, download **historical-forecast** under **Artifacts**. Open `preparation.json`, `validation.json` and `bundle/final/evaluation.json` and answer the same identity and gate questions as for the local candidate. Check the job log for the checkout check and, on a scheduled or manually dispatched run, the standalone tests. [Download a workflow artifact](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts)

The schedule repeats the pinned 2021 replay. It can expose a regression in the workflow. A new promotion decision requires fresh, mature evaluation evidence. If you're working locally, keep the candidate and gate output and record hosted evidence as pending.

## Audit an unfamiliar forecast

Ask a facilitator for a disposable project copy and a recorded forecast for an archived fixture. The facilitator should know the defect and give you the fixture and its run evidence without revealing the change. Use this map to find a check that could disprove a claim.

| Claim | Evidence to start with |
| --- | --- |
| The target and player order are defined, and the command works after installation. | [M0](m0.md) fixture, reverse-order check and wheel run |
| The pinned data rebuilds with the same logical contents, and later information stays out. | [M1](m1.md) preparation report and [M2](m2.md) cutoff and leakage checks |
| Selection precedes final scoring, and model value and repeatability can be checked. | [M4a](m4a.md) trial scores, [M4b](m4b.md) run and artifact recovery, [M4c](m4c.md) final forecasts and paired interval |
| The service uses the specified pair and matches offline predictions. | [M5](m5.md) readiness, image ID and F01 and archive replies |
| Telemetry, label maturity and rollback can be checked. | [M6](m6.md) request clues, quality reports and restored replies |

1. Write down which player the probability refers to, the cutoff, and the model, history and feature-state identities.
2. Choose a claim about that reply and write the expected observation before testing it. Trace the prediction through the code and design a small check you can reason through by hand.
3. Keep the failing observation. Repair the cause in the disposable copy, run the same check again, and rebuild the candidate under a new path. Replay the same fixture so you can explain the effect of the repair.
4. Give a reviewer the starting revision, fixture and artifact identities, failing and passing commands and output, the repair diff, and the evidence that led you to it.

Keep the local candidate and promotion attempt, the hosted run URL if available, and the diagnosis record. CI confirms that recorded checks run. A facilitator should record the learner's diagnosis separately after observing the exercise.
