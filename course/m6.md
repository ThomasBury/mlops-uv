## Follow one request from HTTP to inference

Continue from [M5](m5.md) in the same Bash shell at the repository root. Keep `results`, `bundle`, and `m5` set. Start a fresh local worker with the same model and results, JSON logs, a Prometheus metrics endpoint, and an OpenTelemetry console exporter. The exporter writes spans to a local file through standard output. The exercise uses loopback port 8012 and a new scratch directory.

```bash
m6="$(mktemp -d)"
forecast_uv=(uv run --locked --python 3.12 --group mlops --extra tracing)
cp "$m5/image-id.txt" "$m6/"

(
    set -eu
    export ACEBET_FORECAST_RESULTS="$results" ACEBET_FORECAST_BUNDLE="$bundle"
    export ACEBET_LOG_LEVEL=INFO ACEBET_LOG_FORMAT=json ACEBET_LOG_FILE="$m6/requests.jsonl"
    export ACEBET_METRICS_ENABLED=true ACEBET_TRACING_ENABLED=true ACEBET_TRACE_EXPORTER=console
    "${forecast_uv[@]}" uvicorn acebet.app.historical:create_app \
        --factory --host 127.0.0.1 --port 8012 --workers 1 > "$m6/spans.txt" 2>&1 &
    pid=$!
    trap 'kill "$pid" 2>/dev/null || true; wait "$pid" || true' EXIT

    base=http://127.0.0.1:8012
    curl -fsS --retry 12 --retry-connrefused --retry-delay 1 "$base/readyz" > /dev/null
    curl -fsS "$base/metrics" > "$m6/before.prom"
    for fixture in F01 424816 424816 424816; do
        curl -fsS -D "$m6/$fixture.headers" -H 'Content-Type: application/json' \
            --data-binary @"$m5/$fixture-request.json" "$base/forecast" > "$m6/$fixture.json"
    done
    curl -fsS "$base/metrics" > "$m6/after.prom"
)
```

Find `X-Request-ID` in `424816.headers`, which holds the last archived request's headers. Search for its value in `requests.jsonl`.

- `http_request_completed` gives the HTTP status and wall time in `duration_ms`.
- `forecast_served` gives the response, including the model, history, feature-state digests and returned probability. Compare those four values with `$m5/424816-image.json`. The request ID identifies this HTTP attempt. The forecast ID identifies the fixture, cutoff, surface, players and frozen deployment, so the three archived requests share a forecast ID.
- Use the `trace_id` from `forecast_served` to find the related spans in `spans.txt`. The console exporter prints the ID with a `0x` prefix. Find `forecast.feature_lookup` and `forecast.inference`. Each span records one operation's start and end time. Subtract the timestamps and check that both spans have the `POST /forecast` server span as parent. The worker flushes spans on shutdown.

The request timer wraps the handler and includes work such as validation and response handling. The inference span times the fitted pipeline call. The spans are placed around the same code path that M5 used offline. ## Change one signal at a time

Compare the two saved scrapes with `diff -u "$m6/before.prom" "$m6/after.prom"`. Find four new `POST /forecast` responses with status `200`, one Clay and three Hard forecasts, and four new observations in the probability histogram. Series with labels, such as `surface="Hard"`, first appear when the application records that label value.

| Question | Signal to inspect |
| --- | --- |
| How much traffic arrived? | Divide the increase in `acebet_http_requests_total` for `POST /forecast` by elapsed seconds between scrapes. |
| How often did it fail? | Divide the increase for `4xx` or `5xx` responses by the total increase. Use the request ID to inspect a particular failure. |
| How long did replies take? | Compare `acebet_http_request_duration_seconds_bucket` and its `_count` series. Each `le` bucket includes every request at or below its upper bound. |
| How many forecasts are running now? | Sample `acebet_forecasts_in_progress` during requests. This gauge can rise and fall, so idle scrapes can miss work. |
| What did the worker use? | Where exposed, typically on Linux here, inspect `process_resident_memory_bytes` and the increase in `process_cpu_seconds_total`. |
| Did the mix of inputs or predictions change? | Compare `acebet_forecast_surface_total` and `acebet_forecast_absolute_elo_gap` buckets for inputs. Compare `acebet_forecast_p1_win_probability` buckets for outputs using consistent player order across batches. |

These scrapes describe one process. Restart it and its counters reset. Labels such as route, status and surface give a bounded number of series. Request and forecast IDs belong in the logs because each new label value would create another series. [Metric types](https://prometheus.io/docs/tutorials/understanding_metric_types/) · [Histogram buckets](https://prometheus.io/docs/practices/histograms/)

Predict what will move after each change in [`test_monitoring_signals`](../tests/test_historical_serving.py). The test first sends `Ice` as a surface. Next, it holds `predict_proba` while it reads the in-progress gauge, and releases it after at least 300 ms. Finally, it sends four Hard requests for the same fixture, one with reversed player order.

The handler records surface and probability only after `forecaster.predict` returns. [Forecast handler](../src/acebet/app/historical.py)

A shift in features is input drift. A shift in returned scores is prediction drift. This exercise changes the traffic mix by repeating a fixture, so it can move either distribution without changing the model. A change in how inputs relate to outcomes is concept drift. Investigating it requires enough mature labels from comparable fixtures.

## Score the archived forecast when its label arrives

Match `424816` was played on September 20. The archive assumes the result becomes available at midnight UTC on September 22. Run the quality report one second before and then at that boundary. How many distinct September forecasts should the three archived requests contribute?

```bash
"${forecast_uv[@]}" python -m acebet.historical_monitoring quality \
    "$m6/requests.jsonl" "$results" 2021-09-21T23:59:59Z > "$m6/pending.json"
"${forecast_uv[@]}" python -m acebet.historical_monitoring quality \
    "$m6/requests.jsonl" "$results" 2021-09-22T00:00:00Z > "$m6/mature.json"
cat "$m6/pending.json" "$m6/mature.json"
```

`read_forecasts` validates the recorded forecast ID and puts both orders into the same canonical order before deduplicating. `quality_report` skips forecasts whose cutoff is in the future of the report clock, joins the others to eligible results by fixture, and checks player IDs, surface and cutoff before using the outcome. It groups forecasts by UTC cutoff month, model and history. [Quality report](../src/acebet/historical_monitoring.py)

```python
available = {
    match.match_id: match for match in results if match.available_at <= as_of
}
```

Both reports have one distinct September forecast. F01's 2030 cutoff is beyond both report times. Before midnight, the September row has zero labeled forecasts, zero label coverage, and null loss and calibration. At midnight it has one label and full coverage. The label is `0`, so for a first-player probability of about `0.524194`, the loss is `−log(1 − 0.524194)`, about `0.7427`. The `0.4`–`0.6` calibration bin has one observation, with observed first-player win rate zero. Read coverage and label counts with the scores. One result can verify a join and a loss calculation. Estimating calibration or quality trends takes more fixtures, and selective delays can bias the scored subset. The dates in this exercise simulate archive availability.

## Check the gate, then restore a deployment

Apply the rule from [M4c](m4c.md) to the same 369 final fixtures. `promotion_check` verifies the forecast CSV digest, pairs the scores by match, and resamples whole weeks to estimate the interval for candidate-minus-incumbent loss. Write down which endpoint must be below zero before running either comparison. [Promotion check](../src/acebet/historical_monitoring.py)

```python
"accepted": evidence["interval_95"][1] < 0,
```

```bash
(
    set -eu
    status=0
    "${forecast_uv[@]}" python -m acebet.historical_monitoring gate "$bundle/final" \
        --candidate logistic_tuned --incumbent elo > "$m6/elo-gate.json" || status=$?
    test "$status" -eq 1
    status=0
    "${forecast_uv[@]}" python -m acebet.historical_monitoring gate "$bundle/final" \
        --candidate prevalence --incumbent logistic_tuned > "$m6/prevalence-gate.json" || status=$?
    test "$status" -eq 1
    cat "$m6/elo-gate.json" "$m6/prevalence-gate.json"
)
```

Both comparisons report `accepted: false`. Logistic minus Elo has a mean of about `+0.00340` and an interval of about `[+0.00019, +0.00547]`. Elo scores better on this replay. Prevalence minus logistic has a mean of about `+0.06351` and an interval of about `[+0.03904, +0.08013]`. Prevalence scores worse on this replay. The gate reports evidence. Explicit promotion of a passing bundle writes an approval record, and activation still requires starting a worker with a model and history pair.
