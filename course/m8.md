# M8. Investigate forecasts on a replay clock

One AceBet request was slow. Later, a report showed more Hard-court replies and no new scores. Decide which observation points to a service problem and when you have enough evidence to score a forecast. You'll make both reports from the same JSON Lines capture using Python and SQLite on one laptop.

## Read the capture at two times

Start at the repository root with Bash, uv and Python 3.12 with SQLite 3.38 or later. The [capture](fixtures/m8-incident.jsonl) includes replies from the historical service and the archived result for match `424816`. You can start here without training or starting a server. The capture uses simulated receipt times, real measured durations from an in-process run, and a deliberately delayed delivery of the archived label to the report.

| Field | Question it answers |
| --- | --- |
| `duration_ms` | How much time elapsed while the request or feature lookup ran? The timer uses `perf_counter()`. |
| `forecast.cutoff` | Which facts were eligible when the replay computed the forecast? |
| `observed_at` and `as_of` | When does the simulated observer see an event or outcome, and where does the report stop? |

Follow one line for `forecast_served`. Its `timestamp` is when the app wrote the log during capture. `observed_at` puts it on the lab's replay clock. The archived match keeps its September 2021 forecast cutoff and `archive_available_at` records the source availability assumption. The lab schedules the request and outcome delivery in June 2030. [Archive provenance in M1](m1.md)

Predict what the report will count before you run it. Two Hard replies refer to the same fixture and deployment, including a retry with the players reversed. A fourth request uses an invalid surface. One outcome arrives at midnight on June 12.

```bash
m8="$(mktemp -d)"
capture=course/fixtures/m8-incident.jsonl
replay=(uv run --locked --python 3.12 python course/m8_replay.py)
before=2030-06-11T23:59:59Z
after=2030-06-12T00:00:00Z

"${replay[@]}" "$capture" "$m8/replay.sqlite" "$before" > "$m8/pending.json"
"${replay[@]}" "$capture" "$m8/replay.sqlite" "$after" > "$m8/mature.json"
cat "$m8/pending.json" "$m8/mature.json"
```

| Evidence | One second before midnight | At midnight |
| --- | ---: | ---: |
| Completed or failed requests | 4 | 4 |
| HTTP errors | 1 | 1 |
| Distinct forecasts | 2 | 2 |
| Forecasts with labels | 0 | 1 |
| Label coverage | 0% | 50% |
| Log loss | `null` | about 0.7493 |

In `requests`, find the two Hard replies sharing a forecast ID. The slow attempt spends at least 250 ms in the feature lookup. The retry has its own request ID and a shorter lookup. Find the 422 and its missing lookup time and forecast ID. In `surface_mix`, June 10 has one Clay reply and June 11 has two Hard replies. That change describes the requests served in these two batches. Repeating the archived fixture changes this mix without a change to the model or its inputs for that fixture.

## Trace the count and repair the join

Open [m8_replay.py](m8_replay.py). The importer links the completion, lookup and forecast events by request ID. This lab lets the app generate a fresh ID for every attempt. A primary key on `(kind, event_key)` makes an exact reimport a no-op. The forecast identity comes from the fixture, cutoff, stable player pair and deployment. The importer applies the [existing player-order and retry checks](../src/acebet/historical_monitoring.py) before storing the probability in canonical player order.

`QUALITY_ROWS` first selects forecasts visible at `as_of` whose cutoff has passed. `row_number()` keeps the first visible reply for each forecast ID. Then the query joins the matching outcome, with the maturity condition inside the `LEFT JOIN`.

```sql
LEFT JOIN events AS outcome
    ON outcome.kind = 'outcome'
    AND outcome.observed_at <= :as_of
    -- The full query also matches the fixture, players, surface and cutoff.
```

Try a typical reporting bug in a scratch copy. Move `AND outcome.observed_at <= :as_of` from the join into the final `WHERE` clause, after `f.attempt = 1`. Predict what happens to forecasts with a missing outcome or an outcome that arrived late.

```bash
cp course/m8_replay.py "$m8/broken.py"
# Edit the query in "$m8/broken.py", then run both times against the same capture.
uv run --locked --python 3.12 python "$m8/broken.py" \
    "$capture" "$m8/replay.sqlite" "$before"
uv run --locked --python 3.12 python "$m8/broken.py" \
    "$capture" "$m8/replay.sqlite" "$after"
```

The broken report has no quality group before midnight. At midnight it counts one forecast with one label and reports 100% coverage. Putting the time condition back in the join preserves both forecasts and leaves the missing labels null. Confirm the fixed behavior and the effect of importing the same file twice.

```bash
"${replay[@]}" "$capture" "$m8/replay.sqlite" "$before" > "$m8/reimport.json"
cmp "$m8/pending.json" "$m8/reimport.json"
uv run --locked --python 3.12 pytest -q course/test_m8_replay.py
```

Match `424816` becomes scoreable at the boundary with label `0` and a canonical first-player probability near `0.527281`. Its contribution is `−log(1 − 0.527281)`. The report reuses the [loss and calibration calculations from M4c](../src/acebet/train/historical_evaluation.py). In the only occupied calibration bin, one forecast had a mean probability near `0.527281` and an observed win rate of zero. F01 is synthetic and has no outcome in this replay.

## Generate a fresh capture

Use the candidate directory from [M7](m7.md). If you need one, run `just forecast-candidate "$m8/candidate"` and set `candidate="$m8/candidate"`. The [capture script](m8_capture.py) uses the in-process FastAPI test client to start the same app and send four requests. It wraps `ratings_as_of` for the two archived lookups, sleeps 250 ms on the first, and logs the elapsed time with the request ID. The capture keeps the original log timestamp, assigns each attempt its replay time, and adds the archive outcome at the specified availability time. [FastAPI test client and lifespan](https://fastapi.tiangolo.com/advanced/testing-events/)

```bash
uv run --locked --python 3.12 python course/m8_capture.py \
    "$candidate" "$m8/fresh.jsonl"
"${replay[@]}" "$m8/fresh.jsonl" "$m8/fresh.sqlite" "$after" > "$m8/fresh-report.json"
```

Compare the status counts, surface counts and label coverage with the supplied capture. Check the new scored probability against match `424816` in the new candidate's `bundle/final/forecasts.csv` using [M4c's tolerance](m4c.md). The supplied capture records an earlier fitted model. Request IDs, measured durations and artifact digests identify the new run.

Keep the capture, the two report times, the SQL and a short incident record. Name the slow request and its lookup time, explain why the Hard reply count changed, and record when match `424816` became scoreable. The slow lookup justifies inspecting that code path. The surface mix gives you a cohort to investigate. One observed outcome is enough to verify the join and the loss calculation. A retraining decision needs more mature outcomes and a comparable evaluation.
