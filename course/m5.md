# M5. Serve and package the frozen forecast

A reader sends a fixture over HTTP. How can you tell whether the service used the same fitted pipeline and history as the offline evaluation? Test two fixtures. F01 covers the hand-worked feature trace. Match `424816`, Barrere–Pospisil in Metz, also exercises the bundled archive and has a batch forecast in M4c.

## Establish the offline answers

Use Bash, uv, Python 3.12 and `curl` from the repository root. The checks use loopback ports 8010 and 8011. The container exercise needs Docker with Buildx or native Podman on Linux.

If you completed [M4c](m4c.md), keep `results` and `bundle` set to your canonical Parquet and evaluated bundle. To start directly in M5, unpack the [frozen prerequisite](bundles/m5-prerequisites.tar.gz) into scratch space. It includes canonical history, the fitted pipeline, and the held-out forecasts. Use the bundle from this course checkout because Joblib can execute code when loading a model.

```bash
prerequisite="$(mktemp -d)"
tar -xzf course/bundles/m5-prerequisites.tar.gz -C "$prerequisite"
results="$prerequisite/matches.parquet"
bundle="$prerequisite/bundle"
```

Create a fresh directory for your requests and replies. Run the offline forecaster for both requests before opening the HTTP service.

```bash
m5="$(mktemp -d)"
cat > "$m5/F01-request.json" <<'JSON'
{"fixture_id":"F01","p1_id":"P01","p2_id":"P02","surface":"Clay","cutoff":"2030-06-10T12:00:00Z"}
JSON
cat > "$m5/424816-request.json" <<'JSON'
{"fixture_id":"424816","p1_id":"1985","p2_id":"427","surface":"Hard","cutoff":"2021-09-19T23:59:59Z"}
JSON
for fixture in F01 424816; do
    uv run --locked --python 3.12 --group mlops python -m acebet.historical_forecast \
        "$results" "$bundle" < "$m5/$fixture-request.json" > "$m5/$fixture-offline.json"
done
```

In `FrozenForecast.predict`, the cutoff and surface must match the known fixture. The forecaster sorts the IDs, reconstructs the Elo gap from results available at the cutoff, and passes one row to the saved pipeline. For F01 it uses the synthetic history from the earlier lessons. Class 1 means the smaller ID won in the pipeline's fixed ordering. The last two lines convert that result back to the caller's ordering. [Replay implementation](../src/acebet/historical_forecast.py)

```python
probability = float(self.model.predict_proba(inputs)[0, 1])
if request.p1_id != players[0]:
    gap, probability = -gap, 1.0 - probability
```

F01 should give an Elo gap of −16 and a probability of about `0.475945`. Match `424816` should give about `0.524194`. Allow an absolute difference of `1e-8` for the probabilities and require exact agreement on the remaining response fields. The model digest identifies the fitted pipeline bytes. The history digest identifies the canonical results. The feature-state digest identifies the synthetic trace for F01 and the canonical results used for replay for the archived match. Keep the cutoff, surface and ordered IDs with those digests.

## Put HTTP in front of the same model

Uvicorn accepts HTTP connections and calls the FastAPI application. FastAPI uses the annotation `payload: ForecastRequest` to validate the JSON with Pydantic. A second check inside `predict` rejects requests that are valid JSON with valid field types but inconsistent with the stored fixture. The route delegates to the same `FrozenForecast.predict` used by the offline command. [HTTP handler](../src/acebet/app/historical.py) · [FastAPI request bodies](https://fastapi.tiangolo.com/tutorial/body/)

```python
@app.post("/forecast")
def forecast(payload: ForecastRequest, request: Request) -> ForecastResponse:
    forecaster = getattr(request.app.state, "forecaster", None)
    if forecaster is None:
        raise HTTPException(status_code=503, detail="Forecast assets unavailable")
    # The rest of the handler calls forecaster.predict and records the result.
```

The lifespan hook loads the assets once per worker before accepting requests. `load_forecaster` checks the canonical history, feature configuration and source, inference dependencies and model hash. It checks the fitted pipeline's input columns and class order, then replays F01 against the recorded probability. Use a bundle you trained or obtained from a trusted source. Joblib deserialization can execute code, and a checksum that ships with a bundle only checks consistency. [Startup and loading code](../src/acebet/app/historical.py) · [Bundle checks](../src/acebet/historical_forecast.py) · [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/)

Save a client in the scratch directory. It sends both fixtures concurrently, checks the saved offline replies against HTTP, and compares the archived forecast with the independent batch prediction in M4c. It also changes one input at a time to locate the two validation boundaries.

```bash
cat > "$m5/check-http.py" <<'PY'
import asyncio
import csv
import json
from math import isclose
from pathlib import Path
import sys

import httpx

scratch = Path(__file__).parent
base_url, bundle, source = sys.argv[1:]
fixtures = ("F01", "424816")
requests = [json.loads((scratch / f"{fixture}-request.json").read_text()) for fixture in fixtures]


async def main():
    async with httpx.AsyncClient(base_url=base_url) as client:
        responses = await asyncio.gather(
            *(client.post("/forecast", json=request) for request in requests)
        )
        for fixture, response in zip(fixtures, responses, strict=True):
            received = response.raise_for_status().json()
            expected = json.loads((scratch / f"{fixture}-offline.json").read_text())
            assert received.keys() == expected.keys(), fixture
            for field, value in expected.items():
                if field == "p1_win_probability":
                    assert isclose(received[field], value, abs_tol=1e-8, rel_tol=0), fixture
                else:
                    assert received[field] == value, (fixture, field)
            (scratch / f"{fixture}-{source}.json").write_text(response.text + "\n")
            print(fixture, received["p1_win_probability"], received["model_sha256"])

        with (Path(bundle) / "final/forecasts.csv").open(newline="") as file:
            batch = next(row for row in csv.DictReader(file) if row["match_id"] == "424816")
        for field in ("p1_id", "p2_id", "surface"):
            assert batch[field] == requests[1][field], field
        assert batch["cutoff"].replace(" ", "T").replace("+00:00", "Z") == requests[1]["cutoff"]
        assert isclose(
            responses[1].json()["p1_win_probability"],
            float(batch["logistic_tuned"]),
            abs_tol=1e-8,
            rel_tol=0,
        )

        f01 = requests[0]
        for change in ({"surface": "Ice"}, {"cutoff": "2030-06-10T12:30:00Z"}):
            response = await client.post("/forecast", json={**f01, **change})
            assert response.status_code == 422, response.text
            print(response.json()["detail"])


asyncio.run(main())
PY

(
    set -eu
    export ACEBET_FORECAST_RESULTS="$results" ACEBET_FORECAST_BUNDLE="$bundle"
    uv run --locked --python 3.12 --group mlops uvicorn acebet.app.historical:create_app \
        --factory --host 127.0.0.1 --port 8010 --workers 1 > "$m5/local.log" 2>&1 &
    pid=$!
    trap 'kill "$pid" 2>/dev/null || true; wait "$pid" || true' EXIT
    base=http://127.0.0.1:8010
    curl -fsS --retry 12 --retry-connrefused --retry-delay 1 "$base/readyz"
    printf '\n'
    uv run --locked --python 3.12 --group mlops python "$m5/check-http.py" "$base" "$bundle" local
)
```

Both forecasts should succeed. For `Ice`, the error detail identifies the surface field and its allowed values. For 12:30 UTC, the timestamp passes Pydantic validation, then `predict` rejects the mismatch with the recorded noon cutoff. If the service never becomes ready, inspect `$m5/local.log`.

## Keep liveness and readiness distinct

Liveness asks whether the worker can answer. Readiness asks whether it can serve forecasts. The lifespan hook logs `forecast_assets_invalid` and clears the forecaster when loading fails. Predict the status of each endpoint after replacing the model in a scratch bundle.

```bash
mkdir "$m5/broken"
cp "$bundle/selection.json" "$m5/broken/"
printf 'corrupt model\n' > "$m5/broken/model.joblib"
(
    set -eu
    export ACEBET_FORECAST_RESULTS="$results" ACEBET_FORECAST_BUNDLE="$m5/broken"
    uv run --locked --python 3.12 --group mlops uvicorn acebet.app.historical:create_app \
        --factory --host 127.0.0.1 --port 8010 --workers 1 > "$m5/broken.log" 2>&1 &
    pid=$!
    trap 'kill "$pid" 2>/dev/null || true; wait "$pid" || true' EXIT
    base=http://127.0.0.1:8010
    curl -fsS --retry 12 --retry-connrefused --retry-delay 1 "$base/healthz" > /dev/null
    test "$(curl -sS -o /dev/null -w '%{http_code}' "$base/healthz")" = 200
    test "$(curl -sS -o /dev/null -w '%{http_code}' "$base/readyz")" = 503
    test "$(curl -sS -o /dev/null -w '%{http_code}' -H 'Content-Type: application/json' \
        --data-binary @"$m5/F01-request.json" "$base/forecast")" = 503
    grep 'forecast_assets_invalid' "$m5/broken.log"
)
```

Expect 200 for liveness and 503 for readiness and the valid forecast request. The log identifies the model hash mismatch. Sending traffic based on liveness alone would route readers to a worker that cannot predict.

## Measure what a blocked worker does to another request

An event loop dispatches work for multiple connections. A blocking call inside `async def` prevents the loop from dispatching other requests until the call returns. FastAPI runs a regular `def` handler in a thread pool, which lets the loop dispatch another request while the thread waits. Use one worker and add two scratch routes with the same one-second sleep. Change only the handler declaration and predict what happens to an overlapping liveness request. [FastAPI concurrency](https://fastapi.tiangolo.com/async/)

```bash
cat > "$m5/forecast_lab.py" <<'PY'
from time import sleep

from acebet.app.historical import create_app

app = create_app()


@app.get("/block")
async def block():
    sleep(1)
    return {"done": True}


@app.get("/thread")
def thread():
    sleep(1)
    return {"done": True}
PY

(
    set -eu
    export ACEBET_FORECAST_RESULTS="$results" ACEBET_FORECAST_BUNDLE="$bundle"
    uv run --locked --python 3.12 --group mlops uvicorn forecast_lab:app --app-dir "$m5" \
        --host 127.0.0.1 --port 8010 --workers 1 > "$m5/timing.log" 2>&1 &
    pid=$!
    trap 'kill "$pid" 2>/dev/null || true; wait "$pid" || true' EXIT
    curl -fsS --retry 12 --retry-connrefused --retry-delay 1 http://127.0.0.1:8010/readyz > /dev/null
    uv run --locked --python 3.12 --group mlops python - <<'PY'
import asyncio
from time import perf_counter

import httpx


async def measure():
    async with httpx.AsyncClient(base_url="http://127.0.0.1:8010") as client:
        async def time_health(label):
            start = perf_counter()
            (await client.get("/healthz")).raise_for_status()
            print(f"{label:8} /healthz: {1000 * (perf_counter() - start):.0f} ms")

        await time_health("idle")
        for route in ("/block", "/thread") * 3:
            slow = asyncio.create_task(client.get(route))
            await asyncio.sleep(0.2)
            await time_health(route)
            (await slow).raise_for_status()


asyncio.run(measure())
PY
)
```

The second request usually spends about 800 ms waiting behind `/block`. Behind `/thread` its latency should be close to idle, even though the slow request still takes a second. `await asyncio.sleep(1)` would also yield the loop while waiting. This experiment measures responsiveness during a wait. Replay and inference also do computation. In this CPython runtime the global interpreter lock (GIL) permits one thread per interpreter to execute Python bytecode at a time. Some native numerical routines release it. Extra Uvicorn workers use separate processes, each with its own model and history. Use measured latency, throughput and memory to decide whether to add workers. For a fixed list of fixtures, offline batch prediction can avoid the serving overhead. [Python threading](https://docs.python.org/3.12/library/threading.html) · [Uvicorn worker processes](https://www.uvicorn.org/deployment/)

## Put the verified runtime in an image

The Dockerfile installs the locked dependencies and AceBet in a builder stage. The runtime stage copies the installed environment, supplies the system libraries, and switches to `appuser`. The historical target adds the model, selection record and Parquet. The named build context lets you provide those three files from your scratch directory. The health check for this target probes readiness, where a mismatched bundle surfaces. [Dockerfile](../Dockerfile) · [Buildx named contexts](https://docs.docker.com/reference/cli/docker/buildx/build/#build-context)

```dockerfile
FROM scratch AS forecast_assets

FROM runtime AS historical-forecast

COPY --from=forecast_assets /matches.parquet /selection.json /model.joblib /app/forecast/
```

Prepare the asset directory and choose an image tag for this run.

```bash
mkdir "$m5/image-assets"
install -m 0644 "$results" "$m5/image-assets/matches.parquet"
install -m 0644 "$bundle/selection.json" "$bundle/model.joblib" "$m5/image-assets/"
tag="acebet:m5-${m5##*.}"
```

Build and load with Docker Buildx.

```bash
docker buildx build --target historical-forecast --build-context forecast_assets="$m5/image-assets" \
    --load -t "$tag" .
engine=docker
```

With native Podman on Linux, use this build command instead. Docker image format preserves the health check. Native Podman can run without a daemon. Podman on macOS and Windows uses a Linux VM. [Podman build options](https://docs.podman.io/en/latest/markdown/podman-build.1.html) · [Podman machines](https://docs.podman.io/en/latest/markdown/podman-machine.1.html)

```bash
podman build --format docker --file Dockerfile --target historical-forecast \
    --build-context forecast_assets="$m5/image-assets" -t "$tag" .
engine=podman
```

Run by image ID and publish only to loopback. The image ID is a local content identifier. A registry manifest digest identifies an image when you distribute it through a registry. Reuse the same client so the checks for concurrency, invalid input, identities and probabilities also apply inside the container.

```bash
(
    set -eu
    image_id="$("$engine" image inspect "$tag" --format '{{.Id}}')"
    printf '%s\n' "$image_id" > "$m5/image-id.txt"
    container="$("$engine" run --rm -d -p 127.0.0.1:8011:8000 "$image_id")"
    trap '"$engine" stop "$container" > /dev/null' EXIT
    uid="$("$engine" exec "$container" id -u)"
    mounts="$("$engine" inspect "$container" --format '{{len .Mounts}}')"
    printf 'UID %s, mounts %s\n' "$uid" "$mounts"
    test "$uid" -ne 0
    test "$mounts" -eq 0
    base=http://127.0.0.1:8011
    if ! curl -fsS --retry 12 --retry-all-errors --retry-delay 1 "$base/readyz"; then
        "$engine" logs "$container"
        exit 1
    fi
    printf '\n'
    uv run --locked --python 3.12 --group mlops python "$m5/check-http.py" "$base" "$bundle" image
)
```

Expect a nonzero UID, zero mounts, HTTP 200 for readiness and two forecasts that agree with the offline replies. Keep the requests, local and container replies, and image ID in `$m5` for [M6](m6.md). With these records you can identify the deployed model and feature state when someone reports a surprising forecast.
