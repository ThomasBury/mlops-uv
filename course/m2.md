# M2. Build features as of the forecast cutoff

Matteo Berrettini won on January 7. His next match is on January 9. Should your forecast for that match use the January 7 win? Decide from the time the result became available and the time the forecast had to be ready.

## Work out what F01 knew at noon

Return to [F01](m0.md), the synthetic match between Alex (`P01`) and Robin (`P02`) on June 10, 2030. Both start at Elo 1500. A win against an equally rated player adds `32 × (1 − 0.50) = 16` points to the winner and subtracts 16 from the loser. Use that rule to work out both ratings at noon and again at 12:30 UTC.

| Result or decision | Event date | Available or decided at, UTC |
| --- | --- | --- |
| `F01-prior` originally gives the win to Robin against `P03` | June 9 | June 10 at 11:00 |
| Forecast F01 | June 10 | June 10 at 12:00 |
| Correction gives the `F01-prior` win to `P03` | June 9 | June 10 at 12:30 |
| F01 result gives the win to Alex | June 10 | June 11 at 00:00 |

In `results_as_of`, an original result is eligible at the instant it becomes available. The correction loop visits versions in availability order and stops as soon as a version is later than the cutoff. For an eligible correction, the function replaces the visible record in memory and retains the original event date. Replay then uses the corrected result when it reaches that day. [Replay code](../src/acebet/dataprep/historical_replay.py)

```python
for result in results:
    if result.available_at <= cutoff:
        if result.match_id in known:
            raise ValueError(f"Duplicate original result for {result.match_id}.")
        known[result.match_id] = result
```

```bash
uv run --locked --python 3.12 python -m acebet.dataprep.historical_replay > "$work/f01-trace.json"
cat "$work/f01-trace.json"
```

The trace lists `F01-prior` as the sole contributing result. At noon, Alex is at 1500 and Robin is at 1516. Alex's probability is `1 / (1 + 10 ** ((1516 - 1500) / 400))`, about `0.4770`. At 12:30, Alex is still at 1500 and Robin drops to 1484 because the visible version says Robin lost the earlier match.

## Move the correction across the cutoff

Save this script in your scratch directory. Flip F01's winner, add a future result, and move the correction one minute before noon. Before running it, predict which change can alter the noon ratings.

```bash
cat > "$work/cutoff.py" <<'PY'
from dataclasses import replace
from datetime import datetime, timedelta

from acebet.dataprep.historical_replay import WinnerCorrection, ratings_as_of
from acebet.dataprep.historical_results import MatchResult

noon = datetime.fromisoformat("2030-06-10T12:00:00+00:00")
prior = MatchResult(
    "F01-prior", noon.date() - timedelta(days=1), noon - timedelta(hours=1),
    "Clay", "P02", "P03", "Robin Novak", "New player", 1,
)
current = MatchResult(
    "F01", noon.date(), noon + timedelta(hours=12),
    "Clay", "P01", "P02", "Alex Silva", "Robin Novak", 1,
)
future = replace(
    current, match_id="later", event_date=current.event_date + timedelta(days=1),
    available_at=current.available_at + timedelta(days=1),
)
correction = WinnerCorrection(prior.match_id, "P03", noon + timedelta(minutes=30))

expected = {"P02": 1516.0, "P03": 1484.0}
assert ratings_as_of([prior, current], noon, [correction]) == expected
assert ratings_as_of([prior, replace(current, label=0)], noon, [correction]) == expected
assert ratings_as_of([future, current, prior], noon, [correction]) == expected
assert ratings_as_of([prior, current], correction.available_at, [correction]) == {
    "P02": 1484.0, "P03": 1516.0,
}
assert prior.label == 1
print("Noon and correction-time ratings match the hand calculation.")
PY
uv run --locked --python 3.12 python "$work/cutoff.py"
```

Now change `noon + timedelta(minutes=30)` to `noon - timedelta(minutes=1)` and rerun. The first assertion fails because Robin's corrected rating is already 1484 at noon. Restore the original timestamp and rerun to recover the noon forecast.

`ratings_as_of` groups the visible records by event date. Inside the group it reads the day's opening ratings and collects per-player changes. After the group ends it writes back the sums. [Replay code](../src/acebet/dataprep/historical_replay.py)

```python
for match in day:
    p1 = ratings.get(match.p1_id, INITIAL_ELO)
    p2 = ratings.get(match.p2_id, INITIAL_ELO)
    change = _elo_change(match.label, p1, p2)
    changes[match.p1_id].append(change)
    changes[match.p2_id].append(-change)
for player, deltas in changes.items():
    ratings[player] = ratings.get(player, INITIAL_ELO) + fsum(deltas)
```

If a new player wins twice on the same date against two other new players, both calculations start at 1500 and the new rating is 1532. Updating in the inner loop would make the second calculation depend on match order. The archive replay uses day batches because this exercise assumes no reliable order within a day. [Same-day and cutoff checks](../tests/test_historical_pipeline.py)

```bash
uv run --locked --python 3.12 pytest -q tests/test_historical_pipeline.py \
    -k 'cutoff or same_day or worked_fixture'
```

## Follow Berrettini through the archive

The archive gives us settled results. For this replay we assume each result first becomes available at midnight UTC two calendar days after its event date. Forecasts are made at 23:59:59 UTC on the previous day. These are replay rules. The extract has no observed publication or correction times, and it cannot establish which scheduled fixtures or surfaces were known at the cutoff.

The January 7 result (`369751`) becomes eligible at midnight on January 9. Predict Berrettini's Elo at the cutoff for match `370014` on January 9, then at the cutoff for match `370220` on January 11. Can the two forecasts have the same probability even if their ratings differ?

```bash
uv run --locked --python 3.12 python - "$results" <<'PY'
import sys
from datetime import timedelta
from pathlib import Path

from acebet.dataprep.historical_replay import replay_matches, results_as_of
from acebet.dataprep.historical_results import read_results

history = read_results(Path(sys.argv[1]))
win = next(row for row in history if row.match_id == "369751")
before = win.available_at - timedelta(seconds=1)
assert win not in results_as_of(history, before)
assert win in results_as_of(history, win.available_at)

for match, forecast in replay_matches(history):
    if match.match_id in {"370014", "370220"}:
        assert match.p2_id == "9837"
        print(match.match_id, forecast.cutoff.isoformat(),
              forecast.p1_elo, forecast.p2_elo, forecast.p1_win_probability)
PY
```

| Match | Forecast cutoff, UTC | Opponent Elo | Berrettini Elo | Opponent win probability |
| --- | --- | ---: | ---: | ---: |
| `370014` | January 8 at 23:59:59 | 1500 | 1500 | 0.50 |
| `370220` | January 10 at 23:59:59 | 1516 | 1516 | 0.50 |

Berrettini's January 7 win is visible by the second cutoff. His January 9 win arrives one second after that cutoff. In both rows the opponent is `p1`. Equal ratings give the same probability even though the eligible history has changed.

## Show how leakage buys a better score

F01 eventually gives Alex the win. Predict what happens to his noon probability and his loss if you use that winner to update Elo before forecasting. `leaky_elo_probability` does exactly that using the same noon ratings. Log loss for Alex's observed win is the negative natural log of the probability you assigned to him.

```bash
uv run --locked --python 3.12 python - <<'PY'
from datetime import datetime
from math import log

from acebet.dataprep.historical_replay import (
    MatchForecast, leaky_elo_probability, worked_fixture,
)

trace = worked_fixture()
forecast = MatchForecast(
    trace["fixture_id"], datetime.fromisoformat(trace["cutoff"]),
    trace["p1_elo"], trace["p2_elo"],
)
for probability in (forecast.p1_win_probability, leaky_elo_probability(forecast, label=1)):
    print(f"{probability:.4f} {-log(probability):.4f}")
PY

uv run --locked --python 3.12 python -m acebet.dataprep.historical_replay "$results" \
    > "$work/leakage-comparison.json"
cat "$work/leakage-comparison.json"
```

For F01, the probability moves from `0.4770` to `0.5251` and the loss falls from `0.7403` to `0.6441`. On the same 1,487 archive fixtures before September 1, mean log loss falls from `0.67411` to `0.58933`. The leaky calculation moves each forecast toward its known winner. To repair the ordering, compute the forecast from the visible history and use the current winner only to score it or to update a later cutoff once the result has arrived.
